# Academic Database Approval Decisions

**Purpose:** Give the Naba Academy project owner and academic leadership a concrete, decision-by-decision approval proposal before any production schema migration.

**Status:** Review only. The development assumptions from the October 2026 request are provisional; they are not institutional decisions. The TypeORM migration and catalog API are code artifacts, not approval evidence. No Neon connection, production migration, or institutional data import was performed for this review.

## Status key

- **APPROVED BY EXISTING REQUIREMENTS** — explicitly required by existing project ADRs, roadmap, or compatibility contracts; implementation must comply.
- **RECOMMENDED — NEEDS APPROVAL** — scalable default proposed here, but the institution must accept or amend it.
- **IMPLEMENTED AND TESTED** — present in the provisional code and exercised in isolated tests; does not mean approved for production.
- **BLOCKED** — essential domain, data, authorization, or lifecycle rules are missing; do not implement production writes or claim the capability is ready.

| 2 | Program meaning / major / study plan — **RECOMMENDED — NEEDS APPROVAL** | كلمة «برنامج» قد تعني تخصص الطالب، أو مسار الدرجة، أو خطة الدراسة. الخلط بينها قد يغيّر شروط التخرج. | Define `academic_program` as the admission/placement pathway only. Model majors/specializations and versioned study plans/degree requirements as separate concepts if institutional requirements distinguish them. | Student: placement and graduation audit become understandable. Teacher: course requirements map to the right plan. Administrator: catalog changes do not rewrite old requirements. | **Yes.** Approve the definition and whether separate major, plan, and requirement entities are required. |
| 3 | Credential versus degree level — **RECOMMENDED — NEEDS APPROVAL** | مستوى المؤهل ليس بالضرورة اسم الدرجة أو نوع الشهادة. الجدول القابل للإعداد موجود، لكن لا توجد قيم أو تعريفات معتمدة. | Keep a reference table with immutable code, bilingual labels, effective/retirement lifecycle, and stable references from programs. Separate credential level from award/degree type if both are needed. Do not seed example values. | Student: sees the official pathway award. Teacher: does not infer a curriculum from a label. Administrator: can retire terminology without changing historical records. | **Yes.** Approve definitions, codes, translations, and whether a second award-type dictionary is needed. |
| 4 | Program/credential/catalog identifiers — **RECOMMENDED — NEEDS APPROVAL** | الكود فريد الآن ضمن بعض الجداول، لكن حذف سجل غير مرتبط فعليًا قد يسمح بإعادة استخدام الكود. المطلوب ألا يعود المعرف التجاري بعد تقاعده. | UUIDs are permanent internal keys. Business codes are case-insensitively unique for all time and cannot be physically deleted/reused; use retirement or an immutable code-reservation ledger if hard deletion is allowed. Confirm each code's scope. | Student: old transcripts still identify the same pathway. Teacher: course references remain stable. Administrator: retired codes cannot accidentally identify a new entity. | **Yes.** Approve uniqueness scope, permanent reservation, case/whitespace normalization, and any exceptional reissue process. |
| 5 | Student profile and legacy data — **APPROVED BY EXISTING REQUIREMENTS** | بيانات الكلية والقسم القديمة نصوص حرة؛ لا تثبت أن الطالب يتبع سجلًا جديدًا بعينه. | Keep the five `users` fields and current self-profile response unchanged. Do not backfill or match names/IDs. Add a normalized placement only through a separately verified, approved mapping process. | Student: legacy display remains available. Teacher: no guessed roster/profile data. Administrator: mappings have evidence and review history. | **No approval is needed to preserve legacy data**; **yes** to approve any crosswalk, placement mapping, or response contract change. |
| 6 | Placement and transfer history — **RECOMMENDED — NEEDS APPROVAL** | جدول التطوير يسمح بسجل حالي واحد، لكنه لا يمنع تداخل السجلات القديمة ولا يحدد هل تاريخ النهاية شامل أم غير شامل. | Use immutable effective-dated placement events/versions. Define interval boundaries (recommend half-open `[from, to)`), prohibit overlaps in a transaction/database constraint, retain actor/reason/source, and never overwrite old placements. The current partial unique index is not sufficient. | Student: transfers do not erase prior status. Teacher: course eligibility can be evaluated at the correct date. Administrator: corrections are traceable and reportable. | **Yes.** Approve transfer reasons, effective-date semantics, retroactive corrections, and audit/appeal policy. |
| 7 | Inactive and soft-deleted records — **RECOMMENDED — NEEDS APPROVAL** | هل يظل البرنامج غير النشط ظاهرًا لطالب قديم؟ ومتى يجوز حذف سجل؟ | Never hard-delete records referenced by history. Hide soft-deleted records from normal selection; keep inactive non-deleted records readable by stable ID for historical transcripts. Do not treat inactive placement as current eligibility. Permit retirement only after checking active children and dependent offerings/records. | Student: can understand historical records without being offered an obsolete choice. Teacher: historical course context remains available. Administrator: retirement does not orphan children or history. | **Yes.** Approve visibility, retirement cascade/blocks, and correction rules. |
| 8 | Terms, semesters, and academic calendars — **RECOMMENDED — NEEDS APPROVAL** | يوجد جدول فصل عام، لكن لا توجد سنة أكاديمية أو تقويم مؤسسي أو قاعدة لاختيار الفصل الحالي. | Separate academic year/calendar from term/semester. Give each term stable code, start/end dates, lifecycle, registration/grading windows, time zone policy, and immutable snapshots for completed terms. | Student: knows the authoritative academic period. Teacher: deadlines and grading windows are predictable. Administrator: can operate multiple calendars/campuses if needed. | **Yes.** Approve term vocabulary, academic year relation, date inclusivity, current-term policy, and time zone. |
| 9 | Course, prerequisites, and curriculum — **BLOCKED** | المقرر موجود كتَعريف بسيط، لكن شروطه السابقة غير موجودة؛ ولا توجد خطة مقررات أو قواعد بدائل/مقررات متزامنة. | Add versioned course-to-course prerequisite rules with AND/OR groups, minimum accepted outcome, co-requisite rules, cycle validation, and effective dates. Associate requirements with versioned study plans instead of assuming every program uses the same rules. | Student: receives correct registration eligibility. Teacher: knows course requirements. Administrator: can change curriculum without retroactively invalidating students. | **Yes.** Approve prerequisite semantics, transfer credit, repeat/grade thresholds, and curriculum versioning. |
| 10 | Offering versus section / enrollment — **BLOCKED** | `course_offerings` قد تعني الشعبة نفسها أو مجرد فتح المقرر في فصل. لا توجد شعبة أو تسجيل أو سعة أو انتظار أو انسحاب. | Separate term-level course offering from one or more sections. Enroll a student in a section with unique student/section membership, explicit state history, registration windows, capacity locking, waitlist policy, and auditable add/drop transactions. | Student: sees actual section and registration state. Teacher: sees only assigned section roster. Administrator: capacity and add/drop rules are enforceable. | **Yes.** Approve offering/section definitions, enrollment states, capacity, waitlist, withdrawal, and academic/financial interactions. |
| 11 | Teacher assignment and object scope — **APPROVED BY EXISTING REQUIREMENTS** | الدور وحده لا يكفي؛ يجب أن يثبت النظام أن المدرس مكلف بالشعبة أو القسم المقصود. لا يوجد جدول تكليف مدرّسين. | Require a dated teacher-to-section assignment with role/capacity, effective period, assignment actor, and revocation history. Every roster/content/grading query must check the section assignment and active scope, not just `instructor`. | Student: only their enrolled course staff can access work. Teacher: sees only assigned classes. Administrator/department head: grants/revokes scoped assignments with history. | **The scope principle is already required** by ADR-05; **yes** to approve the assignment roles, periods, and delegation rules. |
| 12 | Assignments, examinations, submissions, and grades — **BLOCKED** | لا توجد جداول لهذه الأعمال. العقود الموجودة في الواجهة لا تعني أن backend أو التخزين/التصحيح موجود. | Model assessments under a section/offering; separate assignment/exam definition, attempt/submission versions, private file metadata, rubric/score components, and published/final grade snapshots. Keep grading and GPA server-authoritative. | Student: sees only own submissions and released grades. Teacher: grades only assigned sections. Administrator: approves final grades and handles appeals with traceability. | **Yes.** Approve grading scale, weights, deadlines/time zones, attempt rules, late work, publication, grade approval, and appeal process. |
| 13 | RBAC, permissions, row scope, and database security — **APPROVED BY EXISTING REQUIREMENTS** | قاعدة البيانات تحفظ نطاق الدور، لكن `RolesGuard` الحالي يتحقق من اسم الدور النشط ولا يثبت نطاق القسم/الشعبة. | Enforce role + permission + scope + resource ownership at the service/query boundary for every student/teacher write/read. Define least-privilege permissions. Add PostgreSQL RLS only if connection identity/context can be set and reset safely per transaction; RLS complements, not replaces, service checks. | Student: own records only. Teacher: assigned records only. | 14 | Audit and historical immutability — **APPROVED BY EXISTING REQUIREMENTS** | سجل placement يحوي من أنشأه ووقت التسجيل فقط؛ لا يسجل سبب النقل أو تعديل/إلغاء القرار. لا يوجد سجل درجات/تسجيل غير قابل للتعديل. | Create an append-only academic audit/event ledger for placement, enrollment, grade changes, approvals, and overrides. Teacher: grading actions are attributable. | 15 | Indexes, checks, and data integrity — **IMPLEMENTED AND TESTED** | توجد مفاتيح أجنبية وفهارس وأكواد فريدة، واختبرت محليًا. هذا لا يغطي كل قواعد المؤسسة، وبعض القواعد بين الجداول لا يمكن فحصها بقيد بسيط. | Retain FK `RESTRICT`, bounded checks, case-insensitive uniqueness, child FK indexes, and transaction-level lifecycle checks. ## Production approval gate

The provisional migration is **not approved for production**. Do not execute it or enable `ACADEMIC_CATALOG_READS_ENABLED` until:

1. All decisions marked approval-required above are recorded by the academic owner and database owner.
2. The schema covers the approved version-one scope, including the approved course/section and enrollment boundary.
3. Audit, historical placement semantics, code reservation, and record-level authorization meet ADR-05, ADR-06, and ADR-10.
4. The revised migration, API contracts, authorization tests, recovery plan, and staging rehearsal are reviewed.
5. A separately authorized change window is approved for the exact target. This review itself does not authorize execution.
